01 · Principio rector
01 · Seguridad por defecto

Tres reglas que no tienen excepciones.

Toda decisión de seguridad del portal se apoya en estas tres premisas.

🚫

No confiar en el navegador

El navegador no es fuente de verdad de acceso. Lo que muestra el frontend no define qué datos puede ver o modificar un usuario. Cualquier dato sensible se valida en el servidor.

Regla 1
🔒

Autorización real en backend y RLS

El acceso efectivo lo resuelven las funciones de Supabase y las políticas de Row Level Security. El frontend solo consume el resultado de ese contrato, no lo define.

Regla 2
🎯

Mínimo privilegio en datos y permisos

Solo se expone lo estrictamente necesario. Sin acceso público a datos operativos. Sin permisos amplios donde bastan permisos acotados. El alcance de cada usuario es el mínimo para cumplir su función.

Regla 3
✅

Consecuencia directa

Un director no puede ver datos de otro establecimiento aunque conozca la URL. Un usuario sin dominio institucional no puede obtener ningún alcance aunque se autentique con Google. Los controles se aplican antes de entregar cualquier dato.

Resultado
Principio rector

02 · Autenticación
02 · Cómo funciona la autenticación

Google OAuth + validación de dominio
en el servidor.

Mecanismo de autenticación
1
El usuario inicia sesión con Google OAuth
Supabase Auth gestiona el flujo OAuth. La sesión se resuelve en el cliente y es validada por Supabase en cada operación posterior.
2
Se verifica el dominio institucional en backend
La función is_portal_allowed_email() comprueba que el correo pertenece al dominio institucional configurado antes de otorgar cualquier acceso.
3
Solo entonces se resuelve el alcance real
Si el correo pasa la validación de dominio, se evalúan los roles registrados en usuario_establecimiento_roles. Sin registro, no hay acceso.
⚠️
Hallazgo importante
El parámetro hd de Google solo es una sugerencia de frontend
Google permite pasar el parámetro hd para pre-filtrar el dominio en la pantalla de login. Pero ese parámetro no es una garantía de seguridad: un usuario con correo de otro dominio puede igualmente completar el flujo OAuth.
No es un control de seguridad
✅
Control real
La validación de dominio es una función del servidor (portal_allowed_email_domain()). Si el correo no pertenece al dominio institucional, ninguna función de acceso devuelve alcance real, independientemente de cómo llegó el usuario al sistema.

03 · Row Level Security
03 · Alcance por datos

Las políticas RLS filtran cada fila
antes de entregarla al usuario.

No es solo control de pantalla: la base de datos aplica el alcance en cada consulta, independientemente del cliente que la haga.

📖
Políticas de lectura
Requieren alcance real de escuela
Tablas protegidas
establecimientos
programacion
actas
actas_invitados
logs
storage.objects
bucket evidencias_actas
La lectura pasa por has_school_scope_access(rbd) o por permisos globales controlados. Sin alcance válido, la consulta devuelve cero filas.
✏️
Políticas de escritura
Requieren acceso de escritura
Control de escritura
La escritura se limita a usuarios con permisos reales sobre la escuela objetivo. Se verifica mediante has_school_write_access(rbd) antes de cualquier INSERT o UPDATE.
Storage: evidencias_actas
La lectura y escritura de archivos PDF en el bucket evidencias_actas se alinea con el alcance real del usuario, no con el estado del cliente ni con la URL del archivo.
Garantía
Un director no puede modificar actas de otro establecimiento aunque intente hacerlo directamente contra la API de Supabase.

04 · Migración de seguridad

Tres cambios que cierran las brechas
de autorización del portal.

Cambio 1
Dominio institucional exigido en backend
Se definen dos funciones nuevas que son la fuente única de verdad sobre el dominio permitido:
portal_allowed_email_domain()
Retorna el dominio institucional configurado
is_portal_allowed_email(email)
Valida si un correo pertenece al dominio institucional
Ninguna función de acceso otorga alcance a correos fuera del dominio, sin importar cómo llegaron al sistema.
Cambio 2
Todas las funciones de acceso redefinidas
Se redefinen para incluir la validación de dominio como precondición:
is_global_admin()
has_global_readonly_access()
current_accessible_rbds()
has_school_scope_access()
has_school_write_access()
get_current_portal_scope()
Cambio 3
Gestión manual de accesos endurecida
Dos funciones de gestión también se refuerzan:
bootstrap_current_user_profile
_from_base_escuelas()
Creación de perfil inicial del usuario
upsert_usuario_establecimiento_rol()
Asignación manual de roles a usuarios
La carga manual de accesos ya no puede registrar correos fuera del dominio institucional configurado.

05 · Hallazgo documentado y resuelto

Acceso anónimo a datos operativos:
identificado y eliminado.

⚠️
Situación anterior
Lectura pública habilitada
La migración 20260416_consejos_public_read_anon.sql habilitaba políticas de lectura anon sobre datos operativos del portal.
Tablas expuestas públicamente
establecimientos Lectura anon
programacion Lectura anon
actas Lectura anon
actas_invitados Lectura anon
Cualquier usuario sin autenticar podía consultar estos datos directamente desde la API de Supabase.
✅
Corrección aplicada
Políticas públicas eliminadas
La migración de hardening ejecuta DROP POLICY IF EXISTS para cada política pública y las reemplaza con políticas que exigen autenticación y alcance real.
🔒
Ninguna tabla operativa devuelve datos sin sesión válida y alcance real asignado.
🎯
Se restaura el principio de mínimo privilegio: lo que no está explícitamente permitido está denegado.
📝
El cambio queda documentado en la migración 20260527_consejos_security_defaults_hardening.sql.
Estado actual
El portal no expone datos públicamente. Solo usuarios autenticados con correo institucional y roles asignados pueden consultar información operativa.

06 · Riesgos y próximos pasos
06 · Pendientes identificados

Cuatro validaciones fuera del código
que deben confirmarse.

Estos riesgos no dependen del código del portal sino de la configuración del entorno de producción.

🗄️
Riesgo 1
Migraciones en entorno real
Confirmar que todas las migraciones de permisos y storage están aplicadas en la base de datos de producción. Una migración no ejecutada deja el entorno en estado anterior al hardening.
Verificar en producción
🌐
Riesgo 2
Configuración CORS
El portal es estático: CORS no se controla desde el código de la app sino desde Supabase, el hosting y el CDN. Revisar que los orígenes permitidos son correctos y no permiten acceso desde dominios no autorizados.
Configurar en Supabase y hosting
🛡️
Riesgo 3
Content Security Policy (CSP)
El portal no tiene una política CSP definida. Un CSP compatible con export estático reduciría el riesgo de inyección de scripts externos. React mitiga XSS por defecto, pero no reemplaza una política global de hardening de cabeceras HTTP.
Evaluar e implementar
🔐
Riesgo 4
Lecturas públicas en nuevas tablas
Si el portal se declara como sistema autenticado, debe evitarse que futuras migraciones vuelvan a habilitar acceso anónimo a datos operativos. El patrón corregido debe replicarse como práctica por defecto en cada nueva tabla.
